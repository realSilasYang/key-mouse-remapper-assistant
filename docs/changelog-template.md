# 📝 中文更新日志模板

**简体中文** | [English](en/changelog-template.md)

新增版本时，把下面的版本块复制到根目录 `CHANGELOG.md` 的“未发布”内容下方，再把已经发布的条目移入该版本。发布物说明必须保留；其余只保留本次实际包含的分类。模板默认不生成“重要说明”，只有存在破坏性变化或用户必须执行的升级操作时才手动加入。

```markdown
## 🎉 版本 [X.Y.Z] - YYYY-MM-DD

### 📦 发布物说明

- **`key-mouse-remapper-assistant-X.Y.Z-source.zip`（完整源码版）**：包含可运行 AHK 源码、应用模块、资源、13 语 README、双语更新日志、测试和构建工具，适合审阅、开发或从源码运行；本机需要 AutoHotkey v2 x64。
- **`key-mouse-remapper-assistant-X.Y.Z-windows-x64.zip`（完整便携版，推荐）**：包含编译 EXE、可编辑映射源码、13 语 README、双语更新日志、许可证、应用模块、界面资源、固定 AutoHotkey v2 x64 运行时及对应源码归档；无需另行安装 AutoHotkey，适合完整解压后长期使用。

---

### ✨ 新增

- **功能名称**：说明新增了什么、适用于什么场景，以及用户可以获得什么。

---

### 🚀 优化

- **功能名称**：说明原有体验或行为如何改变，以及用户能够观察到的具体结果。

---

### 🐛 修复

- **问题名称**：说明原先会出现什么问题，以及修复后的正确行为。

---

### 🔒 安全

- **问题名称**：只在安全修复已经可以公开时保留，说明受影响版本、修复版本和用户是否需要立即操作；不要披露可直接利用的细节。
```

## 📐 编写规则

- 文档标题固定使用 `📋 更新日志`，版本标题固定使用 `🎉 版本 [X.Y.Z] - YYYY-MM-DD`。版本号必须与 `VERSION`、编译文件版本和 Git 标签一致。
- 每个正式版本必须包含 `📦 发布物说明`，逐项给出两个准确文件名、版本定位、包含内容、AutoHotkey 要求和适用场景；按 GitHub 固定展示顺序列为源码 ZIP、便携 ZIP，不能只写“见附件”。
- `⚠️ 重要说明` 是可选章节。只有现有数据或配置不兼容、可能丢失数据、最低环境或权限发生破坏性变化、默认行为带来升级风险，或者用户必须迁移、备份或替换文件时才加入。
- 不得把“保持兼容”“可直接升级”、下载建议、发行物选择、功能简介、一般使用建议或验证范围放进“重要说明”。没有合格事项时连标题一起删除。
- 常规分类固定使用 `✨ 新增`、`🚀 优化`、`🐛 修复`；没有内容的分类直接删除。`🔒 安全` 只在协调披露后使用。
- 更新日志和 Release Notes 均不得包含“✅ 验证范围”章节，也不得罗列测试数量、构建哈希、SHA-256 或未完成的人工矩阵。验证证据留在测试输出、构建日志和 GitHub 资产摘要中。
- 每项先用粗体短语概括功能或问题，再以完整中文说明用户可见变化、适用范围和收益。
- 合并同一功能的零散提交，不直接罗列提交标题、文件名、内部类名、变量名或纯重构过程。只有影响可靠性、性能、兼容性或维护边界时才说明内部变化。
- 配置格式、默认值、权限、系统集成、更新和最低环境发生变化时，必须说明旧数据如何处理、是否需要备份，以及失败后如何恢复。
- GUI、DPI、暗色模式或多显示器变化只描述实际完成的范围，未经验证的组合不得写成已经全面支持。
- 发布版本后更新文件末尾比较链接：`[未发布]` 指向最新标签到 `HEAD`，版本链接指向对应 GitHub Release。

Release Notes 以同一 CHANGELOG 条目为事实源，但把 `📦 发布物说明` 固定放在正文最后，便于用户读完版本变化后直接选择下载。Release Notes 与 GitHub Release 正文不提供 SHA-256。
